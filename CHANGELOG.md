## [0.18.0] - 2026-11-26

### Added
- F-49 (Integrated Dynamics 1.31.5, optional, both sides): a network element whose part no longer exists is skipped on the network's kill and removal paths instead of crashing the server. Integrated Dynamics' networks are world data that outlive their chunks and tick from the server tick; when a network finds its last cable gone it shuts itself down (`killIfEmpty` → `kill`), calling every element's `beforeNetworkKill`, and when an element is removed (`removeNetworkElementPost`) it calls `beforeNetworkKill` and `onNetworkRemoval`; for a part element each reads the part's state through its cable's container, which throws `PartStateException` when the container has no part on that side, and nothing on those paths catches it, while the network's update path does (it logs "Attempted to tick a part that was not properly unloaded" and drops the element). One stale record, a part gone from a cable in a Compact Machine room while the saved network kept its element, took Frostwarf down with "Exception in server tick loop" on 2026-11-26. The three calls are redirected: for a part element whose container is not there or has no part on its side (asked through the element's own container lookup, the same one Integrated Dynamics' call makes an instant later, loading the chunk if that is needed; its one exception, `PartStateException`, is caught) the call is skipped; otherwise it runs inside the smallest `catch (PartStateException)`, which skips as well; the position and side are logged at WARN once per server run, "Integrated Dynamics network had a part on <side> of <pos> in <dimension> that no longer exists; removed it from the network instead of crashing". On the kill path the network is dying, so skipping is the removal; on the removal path the method goes on to drop the element from the network. Nothing that exists is changed and no drop is touched. Applied only beside exactly Integrated Dynamics 1.31.5 with Cyclops Core and Common Capabilities loaded; `skipDanglingParts` under `[integratedDynamics]` in `bsp_mod_fixes-server.toml` (default on, and on before the server config has loaded) turns both fixes off.
- F-50 (Integrated Dynamics 1.31.5, optional, both sides): a part removed from a cable whose carrier has no network at that moment is also removed from the saved network that still lists it. `PartContainerDefault.removePart` has two branches: with the cable's carrier holding a network it removes the part's element from that network before dropping the part; with the carrier's network null it drops the part and the item and tells no network. The carrier is transient: after every chunk load it is null until the cable's delayed ticker re-attaches it, and after a world load every saved network's elements wait likewise. A part removed in that window (a wrench on a part, after a Compact Machine room reloaded) left the dangling element F-49 then met. At the head of `removePart`, when the container has a part on that side and no network, the saved networks are searched for a part element at that position and side, and each found is removed from its network through the network's own removal (the cancellable Pre event, then `beforeNetworkKill`, `onNetworkRemoval` and the Post event; the part still exists, so those run as on a normal removal; the element's `onPreRemoved` and `onPostRemoved`, empty in this build and its add-ons, are not run, and the drop is the carrier-less branch's own); a listener that refuses the Pre event leaves the record, logged once; the part's own removal then proceeds as written. One WARN per position and side per run names what was found. Same gate and switch as F-49. F-29 (the Compact Machines room release) is not at fault: a room release is an ordinary chunk unload and reload, which widens this window without opening it.

### Changed
- Dev only: `-PwithId` on a run loads Integrated Dynamics, Cyclops Core and Common Capabilities (the exact pack files), so `gametest/IntegratedDynamicsGameTests` builds a real cable network and kills it; without them the test checks the pure rules and the gate's skip.

## [0.17.0] - 2026-11-26

### Added
- F-48 (Minecraft 1.20.1, Forge 47.4.23, both sides): a chunk's unload runs its block entities' two passes over copies of the block entity map. `LevelChunk.clearAllBlockEntities` (from `ServerLevel.unload` and `ClientLevel.unload`) called every block entity's `onChunkUnloaded` and then its `setRemoved` while walking the chunk's live `HashMap`, so a hook that changed that map meanwhile made the walk throw `ConcurrentModificationException` at the end of the pass: the rest of the method never ran (the second pass, the clears, the ticker rebinds), the chunk's block entities were dropped without `setRemoved`, its tickers stayed bound, and from the world tick it was "Exception ticking world", the crash Moongrove saw eleven minutes after a start with nobody online. The usual change is a lookup, not a write: `Level.getBlockEntity` on a position in the unloading chunk drops the already-removed entry and creates a new block entity in its place, and every block entity invalidates its attached capabilities in both passes (Forge's `onChunkUnloaded` and `setRemoved` both do; MFFS's electric block entities invalidate their own energy capabilities besides), which wakes any other mod's cache listener that re-reads its neighbour at once; a block change from a hook does the same; the stack never names the listener. The two `forEach` calls over the map are redirected to run the same action over a copy, in vanilla's order (the ticker rebind is untouched); after each call the map's size and the block entity's own entry are checked, and when either moved an identity diff names the block entity at WARN, once per block entity type per server run, as "<type> at <pos> in <dimension> changed its chunk's block entities while the chunk unloaded (+N/-M)", with one diff at the end of each pass for an equal-size change elsewhere (named as the pass's, once per chunk); after the second pass every block entity the pass never saw (added during the unload) gets `setRemoved` too and is named, in up to eight rounds since a removal can wake the same listener and re-create the entry again; a type still coming back after the last round is named at WARN and dropped by vanilla's clear, the one case left half-alive. `unloadOverCopies` under `[chunks]` in `bsp_mod_fixes-server.toml` (default on) turns the rule off. MFFS 5.1.29 needs no change here: it tears no field down on unload (its teardown runs when the projector block is replaced or broken, and from its tick). Not covered: a lookup from another thread, such as the force field block's light reading on the light thread, which can change the map outside any loop. No mod in the pack patches these two loops; Chunk Sending's head injection into the same method is compatible.

## [0.16.0] - 2026-11-25

### Added
- F-47 (Modular Powersuits 2.3.13, both sides): the Rail Gun's cooldown is counted by game time in its own `use`, so it ends 15 ticks after the shot whether or not the module is online. Powersuits wrote `cooldown = 15` into the fist's `MMModItem` compound at each shot and counted it down only in the module's `onPlayerTickActive`, which Numina runs only while the module is online, while `use` itself fired without looking at the online flag: a Rail Gun whose module was offline (its `Active` tag false, by a module toggle key, the Tinker Table's toggle, or possibly Numina's static default at an unlucky lookup, which the measurement did not reproduce) fired once and never again, since nothing counted its cooldown down, until a weapon change rewrote `MMModItem` from the module list and wiped the cooldown with it: "just shot once, and it's needed to change weapon to shoot again". The one cooldown read and the one cooldown write in `use` are redirected: the write keeps Powersuits' tag and stamps, beside it, the game time the cooldown ends at; the read answers the ticks left by that stamp. No stamp (a fist from before the fix, or a compound a mode change just rewrote) means ready, as does a stamp more than a full cooldown plus five ticks ahead (another server's clock, carried over by the inventory sync; the five ticks of slack keep a client whose clock runs a tick or two behind the server's between time syncs from playing a shot's sound the server refuses, and cost a few ticks once on a foreign clock that lands inside them). The per-tick count-down still runs while the module is online and no longer matters, and the stamp stays in the compound after it until the next rewrite. A mode change still resets the cooldown as before. No switch.

## [0.15.0] - 2026-11-25

### Added
- F-45 (Numina 2.3.13, for Modular Powersuits 2.3.13's config spec): Powersuits' Fortune, Silk Touch and Aqua Affinity modules read their settings where Powersuits writes them. Numina's `PowerModule` builds every module's config keys as `Modules.<category title>.<module>.<setting>`, the title from `ModuleCategory.getConfigTitle()`; the three Mining Enchantment modules are built with `MINING_ENCHANTMENT`, titled `Mining_Enchantment`, while Powersuits' own `ServerConfig` spec writes them under `MINING_ENHANCEMENT`'s title `Mining_Enhancement` (beside the AOE pick and the Vein Miner) and writes no `Mining_Enchantment` section at all, which Forge's spec correction would remove if added by hand. So the modules looked up keys the file never has, Numina's `ModuleConfig` answered the code's defaults, and the server's `base_silkTouchEnCon = 2500.0` was never read: Silk Touch drained the code's 50,000 FE every tick it was on (the enchantment modules drain per tick by design), and the three modules' `isAllowed` keys were ignored the same way. With the keys corrected the file's values apply, and one of its defaults differs from the code's: Aqua Affinity's `base_energyCon` is 0.0 in Powersuits' spec (and in the pack's file) where the code charged 50,000 FE a tick, so Aqua Affinity is free until a server sets that key (`docs/CONFIG.md`); Fortune's three values agree in both places. The one `getConfigTitle()` call in `PowerModule`'s constructor is redirected so that `Mining_Enchantment` reads as `Mining_Enhancement` and every other title stays itself; the keys then land in the section the spec writes and the file holds. Read once at construction, like the keys; no switch; one INFO line the first time a module is moved. Powersuits is at fault (its spec and its module classes disagree); the patch sits in Numina because that is where the key is built.
- F-46 (Modular Powersuits 2.3.13, both sides): the Rail Gun fires without starting an item use. Its `use` is a hitscan (drain, cooldown of 15 ticks, heat, ray-trace, damage, all at once), and then, shot or not, called `player.startUsingItem(hand)`; the Power Fist's use animation is the bow pose for every mode and its use duration is the active module's, 25 ticks for the Rail Gun, so every right click drew the Plasma Cannon's charge look for 25 ticks and a click during the cooldown restarted it with nothing fired. Nothing of the Rail Gun reads the use (its release handler is empty). That one call is redirected to a counter: the shot, the cooldown, the sound and the success result are as before, and the player never "uses" the fist. Three things that came with the use go with it: the client no longer slows the player to a fifth of their movement and blocks sprinting for the 25 ticks after a click; a held right button, which vanilla re-clicks only while no item is in use, fires at the cooldown's rate (about every 16 ticks) instead of after each 25-tick use (about every 26); and Forge's `LivingEntityUseItemEvent.Start` is no longer fired for a Rail Gun click (nothing in Numina or Powersuits listens to it). After each click the server takes vanilla's not-using branch and resends the inventory, as for any item that acts on click without a use. No switch. The Plasma Cannon and the Blade Launcher, which charge on the use and read it on release, are untouched.

### Changed
- Dev only: `gametest/RailgunGameTests` holds the MF-42 measurement of the Rail Gun's single shot (`mf42_the_rail_guns_single_shot_measured`, "MF-42:" lines in the GameTest server's log), the record of which is in `docs/TESTING.md`.

## [0.14.0] - 2026-11-24

### Added
- F-43 (MFFS 5.1.29, optional, both sides): a projector selects its field's positions on the server thread. MFFS ran `selectProjectablePositions` through `CompletableFuture.completeAsync` on the common ForkJoinPool, and that method reads the world and shared state while the server thread changes them: with a Fusion module, `FusionModule.beforeSelect` streams `FrequencyGrid`'s plain `HashSet`, which every fortron block entity's load and unload edits, so a player's arrival (the base's capacitors, derivers and projectors loading one after another) threw `ConcurrentModificationException` ("Error selecting force field blocks") and the selection came back empty; the position cache's loader and the Disintegration module read block states, which from a worker thread hop to the main thread and load chunks; `isLoaded`, the other projectors' modes and modules and the projector's own slots were read with no synchronisation. The one `completeAsync` call in `runSelectionTask` is redirected to run the same selection on the server thread between ticks (the server as executor); the field's geometry is still calculated in the background, where it reads only module counts and the level's height. Nothing of MFFS then touches the world or the frequency grid off the server thread. The selection loop's cost moves to the server thread with it: once a field stands, every pass walks every calculated position (MFFS counts only placements against its per-pass quota), a cache lookup each, so a field at F-35's 100,000-block cap costs some tens of milliseconds every tenth tick on the server thread, where it cost the same on the pool before. `selectOnServerThread` under `[mffs]` in `bsp_mod_fixes-server.toml` (default on) turns the rule off. The mixin applies only when exactly MFFS 5.1.29 is loaded with the patched method in place, and is skipped with one log line otherwise.
- F-44 (MFFS 5.1.29, optional, both sides): a force field stays within loaded chunks; no field work loads a chunk. MFFS's selection asked its position cache before it asked whether the chunk was loaded, and the cache's loader read the block state, which loads an unloaded chunk for one tick; so every field position beyond the loaded area pulled its chunk in, the chunk's saved field blocks got block entities and tickers, the chunk unloaded a tick later and every ticker died, and the cache entry's one-minute life brought each chunk back at least once a minute for as long as the projector ticked (on BSP-Moongrove 1.17 million dead tickers in a hundred minutes in the twenty chunks around one projector, the chunks held in memory until AllTheLeaks' hourly clean-up, then the container out of memory). Each placed block's neighbour-shape updates read the next chunk over the same way, so a field crept on through chunks loaded for a tick; `destroyField` read every calculated position, Fusion's `beforeProject` its collected positions, and a field block's own `onLoad` looked its projector up, loading the projector's chunk whenever a field chunk loaded first. Now the selection skips a position whose chunk does not tick blocks (the range a player or a chunk loader keeps, whose neighbours are already present) before any module or the cache sees it, the chunk's answer memoised for the pass; the teardown and Fusion's removals read block states only where the chunk is present; a field block whose projector's chunk is not present stays as saved without loading it (with the projector's chunk present MFFS's check runs as before, so a stale block is still removed). Field blocks in unloaded chunks stay as saved and are completed where missing when their chunk ticks again. Not covered: a teardown or a Fusion removal in a present chunk that does not tick removes blocks whose neighbour updates can pull the next chunk in once (nothing is placed there again, so no repetition); the projector lookups of the chunk packet (F-36's tag), of collision and of light emission still load the projector's chunk when it is absent; with F-43 off the selection, on the pool, judges by presence rather than ticking, since the ticking tracker is the server thread's to read. `fieldStaysInLoadedChunks` under `[mffs]` in `bsp_mod_fixes-server.toml` (default on) turns the rule off. One DEBUG line a minute at most. The mixins apply only when exactly MFFS 5.1.29 is loaded with the patched methods in place (one of them a synthetic lambda of that build), and are skipped with one log line otherwise.
- `./gradlew runGameTestServer -PwithMffs` now also stands a powered projector forty-eight chunks from the tests, in a chunk the test keeps block-ticking by a ticket of its own, with a cube field of 38,402 positions reaching the unloaded chunks around it, and counts the chunk loads beyond the ticket's ring, the field blocks placed and the thread each selection ran on: as shipped (`-PskipFixes=MffsSelectionThreadMixin,MffsLoadedFieldMixin,MffsFusionProjectMixin,MffsFieldBlockLoadMixin`) every chunk the field touches is loaded (27 to 31 beyond the ticket's ring across runs, most of them before the first block stands); with the fixes none, the field complete in the ticking chunk and nowhere else, every selection on the server thread. Two projectors on one frequency with Fusion modules still merge their fields.

## [0.10.0] - 2026-11-18

### Added
- F-38 (Deep Resonance 1.20-5.0.6, optional, both sides): a block placed with no placer no longer crashes Deep Resonance's radiation shielding handler. Deep Resonance listens to Forge's `BlockEvent.EntityPlaceEvent` to notice a shielding block (obsidian, its dense obsidian and dense glass, a lead storage block) going up near a radiation source, and reads the level it needs as `event.getEntity().level()`. Forge declares that entity nullable: a block placed by no entity carries null, and the handler throws `NullPointerException` on the server thread. Ballistix's blasts post that event for every debris block that lands, with the blast's owner as the entity, and a blast lit by redstone, a timer or a chain has none; Neruina then catches the exception, suspends the debris entity and announces an error to every player, and a server without Neruina would crash. Every other listener on that event in the pack, the six in the BSP mods included, tests the entity before using it. A mixin into the handler returns from it at its head when the event has no entity and its own level is not a `Level` (nothing to read the radiation manager from), never cancelling the event itself, and redirects the one `Entity.level()` call to a handler that answers with the event's own level when the entity is null; with an entity nothing changes, and a blast-placed shielding block near a source is still recorded. The first such event of a session is logged once at INFO with the block and its position; later ones are counted. `placeEventsWithoutPlacer` under `[deepResonance]` in `bsp_mod_fixes-server.toml` (default on, read on both sides) turns the rule off: the null entity is then dereferenced as Deep Resonance's own code did, and the same `NullPointerException` leaves the handler (thrown from this mod's redirect handler inside Deep Resonance's method). The mixin applies only when exactly Deep Resonance 1.20-5.0.6 is loaded and its handler class still has the patched method, and is skipped with one log line otherwise.
- `./gradlew runGameTestServer -PwithDr` loads Deep Resonance, McJtyLib and RFTools Base (the exact pack files) in a dev run, so the F-38 test posts a real place event with no entity for an obsidian block through Deep Resonance's real handler: nothing thrown with the fix, the `NullPointerException` of the report with `-PskipFixes=DeepResonancePlaceEventMixin` or the switch off.
- F-39 (Iron Furnaces 4.1.8, optional, both sides): a player's furnace list is replaced when it loads, not appended to, and duplicate entries are dropped. Iron Furnaces keeps on every player the positions of the furnaces they placed (`ironfurnaces:furnaces_list`, read every tick by a Million Furnace with an online owner to find one furnace of each tier), and its capability provider's `deserializeNBT` adds every saved entry to the list it already holds, with no clear and no check, where Forge's load is a restore and every other provider replaces its state. Any second load on the same player doubles the list, and in the pack BSP-InventorySync's restore at login is exactly that: vanilla loads the local player file, InventorySync then hands the network snapshot's capabilities to Forge's `deserializeCaps`, and the list became local plus snapshot on every login, saved to both. On BSP-Moongrove one player's file reached 2,138,192 entries for two furnaces (88.7 MB of NBT); each login froze the server for about four minutes, timed out everyone online and left a `ServerPlayer` behind. Iron Furnaces' own `add` does check the position first; the load is the one unchecked path, and the mod has no Clone handler to fix. ## [0.1.0] - 2026-11-04

### Added
- The project: a Forge 1.20.1 mod that requires Numina 2.3.13 and Modular Powersuits 2.3.13 exactly, on both sides, with a mixin setup for patching them, a startup log of the fixes active in the build, and the headless test harness.
- F-1 (Modular Powersuits): the creative-install packet, which puts a fully charged module into a worn modular item, is refused unless the sender is in creative mode. Powersuits' handler never checked the game mode, so a modified client could install any module in survival. A refused request is logged at WARN with the player's name.
- F-2 (Numina): a module tweak request is clamped to 0..1 before the server stores it; NaN and infinities become 0. The stock slider only sends 0..1 and Numina stored any double unchecked, which the modules' linear properties then multiplied. A clamped request is logged at WARN with the player's name.
- F-3 (Numina): the player tick handler that ticks every worn module runs once per tick, on the START phase. It never checked the phase, and Forge fires the event twice a tick, so jet thrust, module drains and heat cooling were all doubled. Expect jetpack and jet-boots thrust to halve; the pack's server config is re-tuned for that separately.
- F-4 (Modular Powersuits): the player update handler that clamps fall distance and manages suit sounds runs on the living tick only. It subscribed to the base living event, so it ran for every hurt, jump, fall and drop event of every living entity.
- F-5 (Modular Powersuits): Night Vision refreshes its effect when under 220 ticks remain, with a 400-tick effect, so it charges its 100 FE about every 9 seconds. It refreshed when under 500 ticks remained but applied a 300-tick effect, so it charged every tick.
- F-6 (Modular Powersuits): the Kinetic Generator pays its energy-per-block rate for the horizontal distance walked each tick, on the server, and nothing while flying, riding, gliding or airborne, or for a step over one block (a teleport). It sampled one tick in twenty, only when the player was on the ground at that tick, and its "not generating" branch fell through and generated anyway. The pack's rate is re-tuned for real blocks in the server config notes.
- F-7 (Modular Powersuits): the Shock Absorber absorbs the share of a fall its slider sets (0 to 100 %), pays its energy cost per block absorbed, and when the battery holds less it absorbs the part it can pay for. It was all or nothing: a battery that could not pay for the whole fall absorbed none of it, and its multiplier ran up to ten times the fall. Falls of three blocks or less are left alone as before. Powersuits' landing sound for the absorber is not played.
- F-8 (Modular Powersuits): the Energy Shield absorbs part of each hit for energy instead of adding armor points: 4 % per shield point as vanilla armor does, 80 % at most across all shields, at the module's FE per damage point; with less energy it absorbs what it can pay for, and damage that bypasses armor is untouched. Powersuits added the shield to the armor attribute, its energy drain was dead code, and its tick switched the module off for good whenever energy dipped under one hit's cost. The knockback resistance stays, and the module stays on when the battery is low.
- F-9 (Numina, Modular Powersuits): English names. Numina ships its lang file as `us_en.json`, which Minecraft never loads, so every Numina name showed as a raw key; this jar ships `assets/numina/lang/en_us.json` with all of it plus the key category, the field-of-view key as the code names it, and the capacitor, liquid nitrogen and plating component names. Powersuits lacked a toggle-key name for every module and a few GUI keys; this jar ships only those. Both files come from `tools/gen_lang.py`, and `./gradlew check` runs `tools/check_lang.py` on them.
- F-10 (Numina), an option: the server config `bsp_mod_fixes-server.toml` has `suitClearsFire` (default `true`). Numina puts out a burning player who wears or holds a modular item while the suit's heat is under 95 % of its maximum, which makes suit wearers all but immune to fire aspect and flame; `false` lets the fire burn.
- `docs/CONFIG.md`: the server config file of this mod and the Powersuits server config values to re-tune after F-3 and F-6.
